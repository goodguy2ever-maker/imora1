# IMORA 2.0

Строительный проект под полным цифровым контролем — от архитектурного чертежа и сметы до готового объекта.

IMORA 2.0 — единая цифровая экосистема для девелоперов, генеральных подрядчиков и архитекторов. Проект организационно разделён на 3 модуля с одной Vite-сборкой:

1. **Часть 1 (`apps/landing`):** Лендинг и брендинг с интерактивной трансформацией (Чертеж 2D → 3D-BIM спецификация → Реализованный комплекс), калькулятор окупаемости, тарифная сетка и сбор заявок.
2. **Часть 2 (`apps/platform`):** Авторизация, роли, управление сроком доступа и панель компаний. Онлайн-оплата подписки пока не подключена.
3. **Часть 3 (`apps/workspace`):** Инженерный воркспейс: 2D-САПР чертежей стен, версионные сметы, согласование заявок на материалы, план-факт расходов и журнал стройки.

## Стек

- **Frontend:** Vite 7, React 18, TypeScript, Tailwind CSS 3, Lucide React
- **Backend:** Supabase (PostgreSQL, Row Level Security, RPC-функции, Edge Functions)
- **Тема:** Технологичная тёмная (dark architecture mode)

## Структура Монорепозитория

```
imora/
  apps/
    landing/       # Часть 1: Промо-лендинг, интерактивный визуализатор трансформации
    platform/      # Часть 2: Доступ, авторизация, биллинг, супер-админка
    workspace/     # Часть 3: 2D-редактор чертежей, сметы, снабжение, финансы
  packages/
    ui/            # Общие UI-компоненты
    shared/        # Общие хелперы и утилиты
  src/             # Ядро клиентского приложения
  public/
    images/        # Архитектурные чертежи и фото готовых объектов
  supabase/
    migrations/    # Миграции базы данных и RLS-политики
    functions/     # Edge-функции управления пользователями
```

## Переменные окружения

Файл `.env` содержит:

- `VITE_SUPABASE_URL` — URL проекта Supabase
- `VITE_SUPABASE_ANON_KEY` — anon-ключ Supabase

Service-role ключ используется только в edge-функции и хранится в секретах Supabase.

## Миграции

1. **buildai_01_core_access** — компании, профили, журнал аудита, заявки на демо. Хелпер-функции `app.my_company_id()`, `app.is_super_admin()`, `get_my_access()`. RLS и гранты.
2. **buildai_02_workspace_tables** — проекты, версии смет, строки смет, задачи, заявки на материалы, расходы, ежедневные отчёты. Составные FK (id, company_id). RLS по компании и роли.
3. **buildai_03_business_functions** — серверные функции: создание компании, версии сметы, утверждение сметы, workflow заявок, дашборд. Аудит действий.

## Создание SUPER_ADMIN

После применения миграций создайте первого платформенного администратора:

1. Создайте пользователя в Supabase Auth (через панель Supabase или SQL).
2. Вставьте профиль:

```sql
INSERT INTO public.profiles (id, role, full_name, email, status)
VALUES ('<uuid-пользователя>', 'SUPER_ADMIN', 'Имя Админа', 'admin@buildai.ru', 'active');
```

3. Войдите через `/login` — вас перенаправит на `/admin`.

## Создание компании

1. Войдите как SUPER_ADMIN.
2. На странице «Компании и доступ» нажмите «Создать компанию».
3. Заполните данные компании и администратора.
4. Будет создан Auth-аккаунт администратора. До подключения серверной почтовой интеграции передайте реквизиты вручную.

## Edge-функция manage-users

Обрабатывает: `create_company`, `create_team_member`, `update_team_member`, `reset_team_password`. Использует service-role ключ, проверяет JWT вызывающего. Конфигурация в `supabase/config.toml` (`verify_jwt = true`).

## Изоляция компаний

- Каждая таблица данных имеет `company_id`.
- RLS-политики используют `app.my_company_id()` — возвращает компанию только если профиль активен AND компания открыта (статус trial/active AND access_until > now()).
- Приостановленные и истёкшие компании теряют доступ, но данные сохраняются.
- Составные FK (id, company_id) гарантируют, что строки не могут ссылаться на чужие проекты.
- Роли и компания проверяются на сервере, не в браузере.

## Известные ограничения

- Восстановление пароля по email реализовано; перед публичным запуском проверьте SMTP и разрешённые Auth redirect URLs.
- Нет экспорта данных.
- Нет интеграции с внешними системами.
- Мультиязычность только RU.

## Демо-сценарий (5 минут)

1. **Лендинг (30 сек):** Откройте `/`. Покажите заголовок, проблемы, возможности, форму заявки на демо. Нажмите «Войти».

2. **Вход как SUPER_ADMIN (30 сек):** Войдите как платформенный администратор. Вы попадёте на `/admin`.

3. **Создание компании (1 мин):** На «Компании и доступ» нажмите «Создать компанию». Заполните название, статус (trial), дату доступа, лимит пользователей. Введите имя и email администратора компании. Создайте.

4. **Вход как администратор компании (1 мин):** Выйдите, войдите под аккаунтом администратора компании. Вы попадёте в `/app` — дашборд.

5. **Проект и смета (1 мин):** Откройте «Проекты» → создайте проект. Откройте проект → создайте версию сметы → добавьте строки (материал, количество, цена) → утвердите смету.

6. **Заявка на материал (30 сек):** Откройте «Заявки на материалы» → создайте заявку → отправьте на согласование → согласуйте (как админ).

7. **Расход и отчёт (30 сек):** Добавьте расход по проекту. Создайте ежедневный отчёт. Вернитесь на дашборд — покажите бюджет vs факт.

8. **Команда (30 сек):** Откройте «Команда» → пригласите сотрудника. Покажите смену роли и блокировку.

9. **Блокировка (опционально):** Выйдите, войдите как SUPER_ADMIN → измените статус компании на «Приостановлена». Войдите под администратором компании — покажите экран блокировки с сохранением данных.

## Проверка доступа к платформенной консоли

Вход в `/admin` и `/platform-gate` использует Supabase Auth через `/login`.
Консоль открывается только после загрузки серверных прав для активного `SUPER_ADMIN`.
Мастер-ключи и флаги браузерного хранилища для выдачи доступа не используются.
Проверки SQL RLS и Edge Function остаются обязательным серверным уровнем авторизации.

Регрессионные проверки маршрутов (после установки dev-зависимостей):

```bash
node --test tests/platform-access.test.cjs
```

Эти проверки изолируют интерфейс маршрутов с подставленными состояниями Auth;
они не заменяют интеграционную проверку Supabase и RLS.

## Выдача доступа без саморегистрации

Самостоятельная регистрация пользователей не предусмотрена. Заявка на лендинге
не создаёт аккаунт и не выдаёт доступ. Активный SUPER_ADMIN создаёт компанию и
первого COMPANY_ADMIN через manage-users; COMPANY_ADMIN добавляет сотрудников
только в свою компанию. Восстановление пароля относится к существующим аккаунтам.

В supabase/config.toml отключён signup (общий и email). В существующем hosted
проекте Supabase отдельно отключите Authentication → Allow new users to sign up
(или соответствующую настройку регистрации в текущем Dashboard). Изменение
локального TOML само по себе не меняет настройки уже работающего Auth-сервиса.

Для нового сценария активации сначала примените миграцию
20261104114400_imora_08_demo_request_activation.sql, затем разверните обновлённую
manage-users, затем frontend. Создание компании, профиля администратора и
привязка/одобрение заявки выполняются одной SQL-транзакцией. Повторная активация
одной заявки блокируется на сервере. Существующий статус closed сохраняется.
Почтовая ошибка после создания компании не отменяет доступ и не скрывает
карточку реквизитов. Если ответ сервера потерян, обновите заявки/компании перед
повтором; пароль существующего администратора можно восстановить через Auth.

Проверки обработчиков и доступа:

```bash
node --test tests/*.test.cjs
```

SQL-регрессия: tests/demo-request-activation.sql. Запускайте её только на тестовой
БД после миграций от владельца миграций (например, через psql с ON_ERROR_STOP=1).
Тестовые изменения находятся в транзакции и откатываются. Сценарий проверяет
активацию, повтор, полномочия, сохранение closed и откат при сбое обновления.

## Доступ владельца платформы

Адрес консоли: /admin (совместимый вход: /platform-gate). Войдите через /login
аккаунтом Supabase Auth с активным public.profiles.role = SUPER_ADMIN.
Для SUPER_ADMIN company_id должен быть NULL. Email и пароль — от реального
Auth-аккаунта; опубликованные ранее мастер-ключи больше не работают.
Если аккаунта/профиля ещё нет, сначала создайте владельца в Supabase Auth и
назначьте профиль SUPER_ADMIN через доверенный административный доступ.
Назначение роли обычным пользователем или через форму заявки невозможно.

Публичные настройки frontend перечислены в .env.example. Сам файл .env
игнорируется Git. Серверный service_role и секреты SMTP/почтового API нельзя
помещать в VITE_* или клиентский bundle. Для работы через MCP используйте
OAuth-подключение Supabase; копировать секреты из плагина в исходники не нужно.

AuthProvider откладывает запрос прав до завершения обработчика Auth и отбрасывает
устаревшие ответы после выхода/смены пользователя. Проверки используют mock Auth;
перед релизом нужны те же сценарии на реальном тестовом проекте Supabase.

## Рабочие роли и CRM

Миграция `20261104114357_workspace_permissions_and_crm_integrity.sql` согласует
серверные политики с рабочими ролями и добавляет составные связи CRM.
Миграция останавливается на некорректных существующих связях: данные автоматически
не удаляются и не перепривязываются. Перед применением на работающей БД проверьте
её на staging и сделайте резервную копию. Применяйте весь набор миграций по истории.

| Роль | Доступ |
| --- | --- |
| COMPANY_ADMIN | Проекты, сметы, утверждение, команда, закупки, CRM и финансовый учёт компании |
| ENGINEER | Все задачи/отчёты компании, чертежи, редактирование черновых смет и строительные расходы; без утверждения бюджета |
| FOREMAN / MEMBER | Свои созданные/назначенные задачи, свои заявки и отчёты; без смет, финансов и CRM |
| SUPPLY_MANAGER | Свои задачи/расходы, свои и согласованные закупки, заказ/доставка; без изменения согласованного объёма |
| SALES_MANAGER | Назначенные ему лиды, контакты, КП и чтение графиков; чтение объектов недвижимости, без регистрации платежей |
| SALES_LEAD | CRM команды, управление объектами и ручная регистрация полученных платежей |

Справочник проектов (название, адрес и валюта) доступен внутри компании для выбора
объекта в CRM; сметы, чертежи с ценами и расходы защищены отдельными политиками.
SUPER_ADMIN управляет платформой; клиентские данные не раскрываются ему автоматически
через рабочий кабинет. Заблокированные/истёкшие компании теряют доступ через app.my_company_id().

CRM теперь читает и сохраняет данные Supabase: лиды, стадии (с серверным аудитом),
контакты, объекты недвижимости, графики платежей, отметки о полученных суммах и КП.
КП сохраняется как снимок условий; экспорт PDF и автоматический эквайринг не реализованы.
«Получен» в графике — ручная запись уполномоченного сотрудника, не списание с карты.
Суммы группируются по валюте, фиктивных планов выручки нет. Пустая база отображается
пустой, а не демонстрационными клиентами. Оплата подписки отключена до интеграции
провайдера; срок и лимит компании изменяются супер-администратором вручную.

Шахматка: добавление и изменение статуса — COMPANY_ADMIN/SALES_LEAD, чтение — отдел
продаж. Цена объекта пересчитывается сервером. Валюта проекта с финансовыми данными
не меняется без отдельного процесса переноса/конвертации. Чертежи отображают валюту
своего проекта; суммы маркеров пересчитываются из количества и цены.

Проверки: `node --test tests/*.test.cjs`, `npm run typecheck`, `npm run lint`,
`npm run build`. SQL-сценарии tests/workspace-security.sql и
 tests/demo-request-activation.sql запускаются только на тестовой БД после миграций.

## Подключённая база

Frontend подключён к проекту Supabase imora1 (ref: htpiufvtkqjptbmfplpg).
Локальный .env содержит только публичный URL/ключ и не включается в Git.
История файлов миграций согласована с версиями, присвоенными Supabase при первом
развёртывании. Не возвращайте прежние временные имена: CLI может принять их за
новые миграции. Таблицы/RLS развёрнуты, manage-users активна с verify_jwt=true.

Для локального запуска после установки зависимостей: npm run dev.
В ограниченной среде загрузчик vite.config.ts через esbuild может требовать
альтернативу: npm run dev -- --configLoader runner --host 127.0.0.1 --port 5173.
Админка находится по /admin; первый владелец создан отдельно через Supabase Auth,
а его роль назначена административно, без пароля или service-role ключа в коде.
Саморегистрация отключена также в hosted Auth, а не только в config.toml.
Перед размещением на домене настройте Site URL и redirect URLs для восстановления
пароля и выполните сценарии входа/создания компании на опубликованном frontend.
